# YQuake2 hybrid core for MiSTer (Quake II)

@hybrid/CLAUDE.md

## This core

- Name everywhere: `YQuake2` (the engine: core, folders `games/dnk/YQuake2/` and `logs/dnk/YQuake2/`, `_Other/dnk/dnk-YQuake2_*.rbf`, release), `yquake2` (game submodule, binary in `build/`, log, lock). The games and their menu entries (`_Other/dnk-<title>.mgl`): `package/games.txt` (in the zip as `games/dnk/YQuake2/games.txt`, from which the database's build makes the launcher's catalogue).
- The game is the `yquake2/` submodule, branch `mister`. Its MiSTer code is behind the `MISTER_HYBRID` build option.
- Build: `./build.sh` (game), `./core/build_core.sh` (FPGA), `./package.sh` (zip in `dist/`), `MISTER=root@<address> tools/deploy.sh`.
- Release: the zip in `releases/`. Players get it once it is published to the database, only when Danik asks: `hybrid/launcher/distribution.py publish ~/dnk_Distribution_MiSTer releases/YQuake2_YYYYMMDD.zip` (the rule in `hybrid/CLAUDE.md`).
- Try a build on the MiSTer without installing it: `MISTER=root@<address> tools/test_on_mister.sh Q2|RK|GZ|list|nodata|log|stop` (the rule in `hybrid/CLAUDE.md`).
- Lines marked `GAME:` in the scripts and `TODO` in the READMEs are the places the template left for this game.

<!-- Notes that are only true for this game go below. -->

- On GitHub since 2026-10-17: the core is ItsDanik/YQuake2_MiSTer; `yquake2/`, `xatrix/` and `rogue/` are the submodules ItsDanik/yquake2, ItsDanik/xatrix and ItsDanik/rogue (forks of yquake2's), branch `mister` (the packs': the cheats, below). In each, `origin` is the fork and `upstream` yquake2's. yquake2's `CONTRIBUTING` says code written with LLMs is not welcome there: nothing of ours goes upstream. The forks, their `mister` branches and the core repository are still to be made; ask first.
- Built with CMake (`MISTER_HYBRID=ON`, `yquake2/CMakeLists.txt`): one binary `quake2` with the software renderer linked in, and `baseq2/game.so`. The renderer's files are linked into one object with `ld -r` and `objcopy --localize-hidden`, leaving only `GetRefAPI` global (they have their own copies of `shared.c` and friends); `vid.c` calls it as `RefSoft_GetRefAPI`. The mission packs' `game.so` are built from their repositories (`build.sh`, with `-DMISTER_HYBRID` for the cheats). No GL renderers, OpenAL, cURL, XDG or `q2ded`.
- `-DCMAKE_C_FLAGS` replaces the toolchain file's `CMAKE_C_FLAGS_INIT`, so `build.sh` repeats `-mcpu=cortex-a9 -mfpu=neon -mfloat-abi=hard -fno-pie` with `-marm`.
- Video: the soft renderer draws 8 bit; with `MISTER_HYBRID` it copies each frame into an INDEX8 window surface and sets the surface's palette when the renderer's changes (`RE_FlushFrameMiSTer()`, `sw_main.c`), so the FPGA does the colours. Every frame is shown (no partial refresh). The mode is 320x200 or 320x240, the OSD's *Resolution* (status bit 24, `MiSTer_GameHeight()`, `MISTER_HYBRID_HEIGHT=200|240` for a test), whatever `r_mode` says (`RE_SetMode()`); `RE_BeginFrame()` sets the mode again when the option changes, as yquake2 does for a vsync change, so it applies at once. `vid_renderer` is always `soft`. The picture is 4:3, so a pixel is 1.2 times as tall as wide: `R_PIXEL_ASPECT` (`ref_shared.h`) divides the renderer's `yscale` (also the gun's and the particles'), and `cl_view.c` works `fov_y` out for the taller picture.
- Pacing: `Qcommon_Mainloop()` (`frame.c`) waits for the core (`MiSTer_WaitFrame()`) and gives `Qcommon_Frame()` the fields that passed as time (16768us each); while paced every pass is a render and a packet frame.
- Frames are drawn a field ahead (`DRAW_AHEAD` 1 in `mister_port.c`, the template's: the frame for field F started once the counter is F - 2, handed over with `MH_PresentAtField(F)`; one field more latency). The framework's comparison (host version 13, 2026-10-17, on the MiSTer at 320x240, `MISTER_HYBRID_PACE=1`, in turns, frames per 300 shown twice / never shown, averaged over the 300-frame windows): the recorded demo replay (`q2demo1.dm2`) the old way (`MISTER_HYBRID_AHEAD=0`) 24.2 / 21.7 and 21.7 / 18.4, drawn ahead 10.4 / 5.1 and 9.6 / 4.1; the start of `demo1` standing 14.0 / 16.2 and 1.5 / 1.3. Frames per second the same (replay 58.2 to 58.5, `demo1` 59.0 and 59.1): the frames take 12 to 13ms of the field's 16.8, and the slower ones missed their vblank. Drawing ahead stays. `tools/bench.sh` runs in `tools/test_on_mister.sh`'s folder and core (`/tmp/yquake2_test`, set up first if it is not there), not the installed port.
- The MiSTer file is `yquake2/src/backends/mister/mister_port.[ch]`: the game's choice, the HUD rows, the cheats, pacing, exit codes. The choice comes before Quake II's signal handlers, so the launcher's SIGTERM still ends it.
- Games (host version 13, Danik 2026-10-17): a menu entry each, `package/games.txt`: `Q2` Quake II (`baseq2`), `RK` Q2: The Reckoning (`xatrix`), `GZ` Q2: Ground Zero (`rogue`); the demo (`DEMO`, `baseq2` too) has none, Quake II's starts it when the full game is not there. `MiSTer_SelectGame()` picks with `MH_PickGame()` and adds `+set game <dir>` for a pack; then "Loading <title>...". The full game and the demo both have `baseq2/pak0.pak`, so they are told apart by its size (`FullGame()`: the demo's is 50MB, the full game's 180MB on the CD, Steam and GOG; over 100MB is the full game) and given `NULL` or `MH_NOT_THERE` as their files; a pack needs the full game and its `pak0.pak`. Our `game.so` is in the package and says nothing. Checked on the PC with the demo and with stand-in files for the full game and the packs (a sparse 183MB `pak0.pak`): every entry, the list, the messages (2026-10-17).
- HUD margins (host version 13): at 320x240 the layout's `yt` and `yb` (`SCR_ExecuteLayoutString()`, `cl_screen.c`: the status bar, the help icon, the frags) are from the HUD rows (`MiSTer_HudRows()`), and so are the notify lines at the top (`Con_DrawNotify()`); `xv`/`yv` (inventory, field computer) stay in the middle. The view is all 240 rows behind the status bar, as in Quake II at any size. At 320x200 the rows are the screen's edges and the lines are greyed out (mask bit 0, `HudLines()`). - *Cheats* (Danik, 2026-10-17; single player only): God Mode, No Clipping, Invisible to Monsters, Infinite Ammo (status bits 25..28) and the triggers Give All, Quad Damage, Invulnerability, Next Level (`T[56]`..`T[59]`). The engine (`CL_MiSTerCheats()`, `cl_main.c`, every frame) puts the switches into the cvar `mister_cheats`, which each game's library applies every frame (`MiSTer_Cheats()` in `g_main.c` of yquake2, xatrix and rogue, the same code): a switch that is on is set on the player (`FL_GODMODE`, `MOVETYPE_NOCLIP` while alive, `FL_NOTARGET`), one that is off cleared, so the OSD decides (the console's `god` and the like are overridden); Infinite Ammo is `dmflags`' `DF_INFINITE_AMMO`, which the weapons honour in single player. The triggers are the games' commands, sent while a level of a single player game runs (dropped otherwise): `give all`, `give quad damage`, `give invulnerability`, and `mister_nextlevel` (`g_cmds.c` of each game), which uses a `target_changelevel` of the level as if the player had reached it: the first whose map is not the level the player came from (the games' units go back and forth; `mister_prevmap`, from `level.mapname` changing), else the first. `MISTER_HYBRID_CHEATS=<bits>` fixes them for a test (16 Give All, 32 Quad, 64 Invulnerability, 128 Next Level, once a level runs). Checked on the PC with the demo: Give All, and fakecore's `trigger` for all four (Next Level `demo1` to `demo2$base1` and on to `demo3$base2b`; no "unknown item" for Quad and Invulnerability); the switches and the packs not played.
- `-portable` (launch script): `config.cfg` and `save/` go into `games/YQuake2/baseq2/` (or the pack's folder).
- Pad: `MiSTer_AddMappings()` (`client/input/sdl2.c`) makes the core's joysticks SDL game controllers (J1 = a, b, x, y, leftshoulder, rightshoulder, back, start; Menu OK / Back are paddles; L3 / R3 leftstick / rightstick). In the menus the paddles confirm and go back and A / B do not (`Key_GetMenuKey()`, `menu.c`): the Menu OK button is also a face button. `Key_MiSTerLayout()` (`cl_keyboard.c`) sets the default controls once per `MISTER_LAYOUT` (archived cvar `mister_padlayout`): every pad button, and the keys and mouse buttons of its list (WASD, Space, Ctrl, Shift, Mouse 1, 1 to 0 and `-`, Danik's layout of 2026-10-15; the other keys stay as Quake II's `default.cfg` has them), `freelook` on, and `cl_run` on at the first start. The number keys are `use <weapon>` in Quake II (the inventory shows a key bound so as the weapon's hotkey) and in a mission pack `cycleweap` with the pack's weapons of the same place (yquake2's quickswitch groups); the layout is applied per game, as each has its own `config.cfg`. The stick clicks are SDL's leftstick / rightstick (buttons 30 and 31 of the hybrid library, host version 11); L3 drops the item, R3 has nothing. A d-pad press is dropped in the game while the left stick points its way (`MiSTer_StickHoldsDpad()`). No haptic subsystem in the core's SDL: `SDL_Init` without `SDL_INIT_HAPTIC`.

## Speed (2026-10-15)

- Measuring, as in the Xash3D core: `MISTER_HYBRID_FPSLOG=1` logs every 300 fields the frames shown, how many fields apart they came and the milliseconds per stage (`MISTER_MARK()` in `common.h`: input, server, client, render, hud, blit, sound); `MISTER_HYBRID_PROFILE=<file>` samples the game thread's program counter (`mister_port.c`). `MISTER=root@<address> tools/bench.sh <name> <seconds> <arguments>` runs one scene on the MiSTer (settings in `/tmp/yq2bench`, the player's untouched), `tools/benchmark.sh <name> [<environment>]` the standard three (the demo's recorded `q2demo1.dm2`, the same frames every run, and standing at the start of `demo1` and `demo3`), `tools/benchsum.py` and `tools/profile.py` read them. `build/bench/lib` has the MiSTer's libc and libm for the profile's symbols.
- Work per frame (ms) before and after, 320x200: replay 18.33 / 12.31 (50.4 / 59.0 frames per second), demo1 15.86 / 11.67, demo3 11.97 / 8.88. At 320x240 the replay is 57.7 to 58.6 frames per second. Run to run the replay varies by about a frame per second: compare builds in turns.
- What did it, each step measured on the replay: `R_ApplyLight` inline (it was a call per texel of the surface cache and the models; 0.4ms); a helper thread on the second core (`sw_jobs.c`, from the Xash3D core's `r_jobs.c`) that draws the texture spans of the solid surfaces (2.3ms), then also builds their surface cache blocks (2.3ms); `(int)ceil()` inline (`R_CeilInt`, no libm call; 0.25ms); the triangles of the models as ordered jobs (0.8 to 1.0ms). The span step's division is a multiplication (`D_DivSpan`: the Cortex-A9 has no divide instruction), within the noise. The z of the spans in the job too: no change, kept (the threads take whichever work is left).
- World jobs: per solid surface the game thread decides on the cache block (`D_CacheSurfaceDeferred`: allocation and `R_JobsDrain()` before a block that a job of this round may read is reused or rebuilt, `surfcache_t.jobs_round`), works out which spans write z (`D_MarkZSpans`, in order: `VID_DamageZBuffer` depends on the spans before), and queues a job that builds the block (`D_BuildSurface`, with the light buffer and the builder's state per thread, `R_THREAD`), draws the texture and the z. All done before `D_DrawSurfaces` returns.
- Model jobs (`sw_alias.c`, "MODELS AS JOBS"): the game thread transforms a model's vertices into its own part of `finalverts` and queues its triangles, which run one at a time in order (`R_JobsOrdered`) on the helper while the game thread sets up the next. The rasterizer's state is per thread (`sw_polyset.c`; its edge tables point at the thread's own vertices, built at first use), and the job carries what it reads of the setup (skin, span function, blend colour, the projection's scales, which the weapon changes). Sprites, beams and null models wait for the jobs before them (`R_JobsDrain()`).
- Checks, on the PC and the MiSTer, 0 differences: `MISTER_HYBRID_SPANCHECK=1` draws every surface's spans and z again on the game thread once its job is done and before any cache block changes (147 million pixels); `D_DivSpan` against `/` (17 million quotients); `MISTER_HYBRID_MODELCHECK=1` draws each entity pass with the jobs and again without, from the same frame and z buffer (16 million pixels). `MISTER_HYBRID_NOJOBS=1` turns the helper off.
- PGO (`tools/pgo.sh`, `PGO=generate|use|off ./build.sh`, as in the Xash3D core) gained nothing measurable (13.16 / 13.20ms, 14.19 / 13.95ms) and is not used: `build/pgo` is not there, so `build.sh` builds without.
- Not done from the Xash3D core's list: splitting the edge scan between the threads (the world's edges and BSP are about a fifth of the game thread), and the two-stage model jobs (the vertex stage is a few percent here). The frame goes to the core through a copy (`SDL_MISTER_DIRECT` is in a Hybrid_MiSTer commit of the Xash3D core's that is not on `main`); at 8 bits it is 64KB, 0.4ms of blit with the palette.
- A stall of 10 to 20ms every few seconds (in every frame log's slowest frame, stage input): `MH_MenuButtons()` (`hybrid/hps/mister_joymap.c`), which the SDL driver calls every frame, read the controllers' mapping files on the SD card every two seconds, and for a controller without one the whole of `config/inputs/`. It now does that again only when the controllers, those folders or the files it read have changed (a `stat` each, under 1ms). Fixed in Hybrid_MiSTer (17c94c3, 2026-10-15) for every hybrid core.
